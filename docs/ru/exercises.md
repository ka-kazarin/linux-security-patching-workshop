# Задания для самостоятельной проработки

Воспроизводимо на облегчённом стенде: `make up-lite` (2 VM, только stage).
Часть заданий (1) работает вообще без стенда — на примерах в `scan/examples/`.

## 1. Уязвимость без патча → компенсирующая мера

Прогони `make delta` и открой `results/delta.html`. Найди в реестре
(`results/delta.csv`) находку со статусом `open`, для которой на слое ОС нет
патча (подсказка: слой `app`, владелец `dev`). Предложи компенсирующую меру, которая
закрывает риск до выхода патча. Обоснуй, почему это `mitigated`, а не `closed`.

## 2. Узкое WAF-правило под CVE + доказательство тестом

Возьми `waf/modsecurity/wp2shell.conf`. Объясни, почему правило узкое (что именно оно
матчит) и почему не ловит легитимный трафик WordPress. Затем добейся, чтобы
`test_vulnerability.py` был **красным** до `make waf-on` и **зелёным** после. Тест —
это и есть верификация виртуального патча.

## 3. Находка в реестре: владелец и SLA

Добавь в лист `Registry` (Google Sheets по шаблону) свежую находку из отчёта Trivy.
Проставь слой, владельца (инфра/DBA/dev), severity, дату обнаружения и целевой
SLA-срок по матрице `SLA`. Определи по формуле, просрочена ли она.

## 4. Пайплайн stage → prod: зачем verify

Прогони цепочку `make scan-before → make patch ENV=stage → make verify →
make scan-after`. Затем `make rollout`. Объясни своими словами: почему `verify`
обязателен **перед** `rollout` и что именно он гарантирует. Что произойдёт, если
пропустить его и раскатить сразу на prod?
