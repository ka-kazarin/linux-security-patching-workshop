# Results

Output of the live steps (`make scan-before/after`, `make scan-delta`, `make
verify`, `make attack`) lands here. These files are **generated, not
committed** — everything in `results/` is gitignored except this README.
Regenerate them before the event and keep them on disk as the webinar's
insurance policy: if a live run misbehaves on stage, the last successful
run's artifact is still a presentable fallback — it just doesn't live in git.

| File | Insures against | Generated by |
|------|------------------|--------------|
| `patch-plan.json` / `patch-plan.html` | the `make patch-plan ENV=prod` step | `ansible/patch-plan.yml` against the live VMs — freezes pending SECURITY updates as exact `{name, version}` pairs per host, installs nothing. One file (no env suffix): collect it against prod's real pending set, test the same plan on stage (`make patch ENV=stage`), then `make rollout` re-applies it verbatim to prod so prod never resolves a possibly-drifted set of its own. HTML has a collapsible section per host. An empty `packages` list per host is a legitimate result (already patched), not a failure. |
| `delta-<env>.csv` / `delta-<env>.html` | the `make scan-delta ENV=...` step | `python3 scan/delta.py` on `results/scan-{before,after}-<env>.json` (needs those two scans to exist first) |
| `scan-before-<env>.html` / `scan-after-<env>.html` | `make scan-before/after ENV=...` | Trivy via Ansible (`ansible/scan.yml`) against the live VMs. Tagged with ENV so stage and prod never overwrite each other — a delta is always an env's own before vs after |
| `verify.html` | `make verify` | `pytest --html` |
| `attack.log` | `make attack` | PoC output (during stand provisioning, isolated) |
| `bench-before.json` / `bench-after.json` | `make bench-before/after` (stage only, no ENV) | `vegeta` (nginx static + WordPress home page, fixed sub-saturation rate) + `sysbench oltp_read_only --rate=N` (MySQL) via Ansible (`ansible/bench.yml`) against web-stage/db-stage — 1 warmup run (discarded) + 2 timed runs per metric, sampled at an interval into a p50/p95-latency + success-rate time series at a rate held below each endpoint's ceiling, so latency stays flat instead of chasing whatever throughput a noisy host allows; mon/web-prod/db-prod are paused for the run to remove CPU contention. `make bench-delta` (`scan/bench_compare.py`) prints the before/after **median p95**+success-rate/delta table (verdict driven by median p95 and success rate) and renders a p95-latency sparkline (before vs after overlaid) per metric in `results/bench.html` |
| `change-log.jsonl` / `change-log.html` | the `make patch`/`rollout`/`patch-wordpress`/`patch-reboot` steps | `scan/change_log_append.py` appends one JSON-Lines record (what/where/when/who, exact package/version pairs when the action is plan-driven) after each of those targets succeeds — a CMDB/change-management stand-in. `make change-log` (`scan/change_log_report.py`) renders it as a month-by-month HTML calendar, one collapsible entry per event, with a client-side search box (host/package/action/who). Seeded from the tracked `scan/examples/change-log-seed.jsonl` on first run so the calendar has ~3 weeks of history from a fresh clone. Unlike everything else in this table, the `.jsonl` file is **not** removed by `make clean-results` — it's the actual history, not a regenerable report; only `change-log.html` is |

All of these are produced once the stand is built and scanned, and refreshed
before the event. `python3 scan/delta.py` run directly (no `--before`/
`--after`) defaults to the small samples in `scan/examples/` instead — handy
to sanity-check the script itself without a stand, but that is a different
invocation from `make scan-delta`.

## Fun fact: why the DB node runs Oracle Linux 9, not 10

The stand deliberately runs Oracle Linux **9.6** on `db-stage`/`db-prod`,
not the newer 10. Worth mentioning live, not a workaround to hide: Trivy can
report 0 vulnerabilities on Oracle Linux 10 even with a same-day-fresh
vulnerability DB — verified live (2026-09-06): `trivy version` showed the DB
downloaded hours earlier, `pkg_num` detected 517 packages correctly, and the
scan still returned 0. Not a bug in `ansible/scan.yml` — Trivy's Oracle
advisory coverage has historically lagged behind brand-new Oracle Linux minor
releases (the same pattern was reported for 8.5 shortly after its release).
Switching to 9.6 fixed it outright — confirmed live, real findings on every
scan (see `scan-before.html`/`scan-after.html`).
