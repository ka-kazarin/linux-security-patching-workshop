# Results

Output of the live steps (`make scan-before/after`, `make scan-delta`, `make
verify`, `make attack`) lands here. These files are **generated, not
committed** — everything in `results/` is gitignored except this README.
Regenerate them before the event and keep them on disk as the webinar's
insurance policy: if a live run misbehaves on stage, the last successful
run's artifact is still a presentable fallback (the "fallback for every
step" principle, AGENTS.md §2.7) — it just doesn't live in git.

| File | Insures against | Generated by |
|------|------------------|--------------|
| `delta.csv` / `delta.html` | the `make scan-delta` step | `python3 scan/delta.py` on `results/scan-{before,after}.json` (needs those two scans to exist first) |
| `scan-before.html` / `scan-after.html` | `make scan-before/after` | Trivy via Ansible (`ansible/scan.yml`) against the live VMs |
| `verify.html` | `make verify` | `pytest --html` |
| `attack.log` | `make attack` | PoC output (during stand provisioning, isolated) |
| `bench-before.json` / `bench-after.json` | `make bench-before/after` | `wrk` (nginx static + PHP-FPM/WordPress) + `sysbench oltp_read_only` (MySQL) via Ansible (`ansible/bench.yml`) — 1 warmup run (discarded) + 2 timed runs per metric, sampled at an interval into a throughput/latency time series; smoke-level load baseline, not a rigorous benchmark; `make bench-delta` (`scan/bench_compare.py`) prints the before/after **median**+p90/delta table (verdict driven by median, p90 shown for context) and renders a throughput sparkline (before vs after overlaid) per metric in `results/bench.html` |

All of these are produced once the stand is built and scanned, and refreshed
before the event. `python3 scan/delta.py` run directly (no `--before`/
`--after`) defaults to the small samples in `scan/examples/` instead — handy
to sanity-check the script itself without a stand, but that is a different
invocation from `make scan-delta`.

## Fun fact: why the DB node runs Oracle Linux 9, not 10

The stand deliberately runs Oracle Linux **9.6** on `db-stage`/`db-prod`,
not the newer 10. Worth mentioning live, not a workaround to hide: Trivy can
report 0 vulnerabilities on Oracle Linux 10 even with a same-day-fresh
vulnerability DB — verified live (2026-09-06): `trivy version` showed the DB
downloaded hours earlier, `pkg_num` detected 517 packages correctly, and the
scan still returned 0. Not a bug in `ansible/scan.yml` — Trivy's Oracle
advisory coverage has historically lagged behind brand-new Oracle Linux minor
releases (the same pattern was reported for 8.5 shortly after its release).
Switching to 9.6 fixed it outright — confirmed live, real findings on every
scan (see `scan-before.html`/`scan-after.html`).
